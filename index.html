Multi-user editing for Blender that holds up in production.

Kiln puts several artists in one .blend session: shared transforms, locks, comments, snapshots — and a same-session compute pool that borrows idle machines for renders and bakes. Self-hosted with one command. No cloud account.

01 — Live sync

Synchronise operations, not files.

Sending whole .blend files on every edit is slow and unmergeable. Kiln sends small ordered operations over WebSockets from an authoritative server: each op gets a sequence number, clients apply idempotently and drop their own echoes.

OpWhat it carriesNotes
object.upsert / removeStable kiln_id, type, name, parentRename-safe; tombstones on delete
transformloc / rot / scale, visibilityPartial updates allowed, last-writer-wins per field
mesh.replaceverts + polys, full replaceCapped at 50k verts; push on edit-exit, not per keystroke
lock / presence / comment / snapshotHolder, cursor, body, scene dumpSoft locks; presence at 2 Hz; snapshots for restore

Design decisions worth knowing

  • Stable IDs. Every object gets obj["kiln_id"] (UUID). Rename and reparent without forking.
  • Authoritative server, dumb clients. First-seen wins sequence order. No CRDT yet — predictable beats clever at 2–10 users.
  • Stdlib-only addon. Blender's embedded Python often lacks pip, so the WebSocket client is raw sockets. No dependency install step.
  • Main-thread discipline. Network thread → queue → bpy.app.timers. bpy is never touched off-thread.

What it won't do (yet)

  • No per-vertex deltas — large sculpts go via snapshot, not live stream.
  • No undo sync — remote edits arrive as new ops, not local undo steps.
  • No permissions beyond soft locks. Room members are trusted.
02 — Shared compute

The session is the farm.

Only machines already in the room can contribute — no outside workers, no job uploads. Because every sharer holds the same synced scene, a job is just parameters: frames 1–24, tiles 2×2 of frame 7, bake physics. Workers render their local copy.

room "demo" ── members: anand(4cpu) · bob(16cpu+GPU) · mei(32cpu)
job frame[1..4] ──► task:f1→anand · task:f2→bob · task:f3→mei · task:f4→waiting
job bake[physics] ──► assigned: mei (highest score) · others: wait
disconnect ──► leases expire (60–120s) ──► tasks return to waiting
ModeSplitAssignment
Frame farmOne task per frame (max 32/job)Greedy claim; best waiting task per worker
Tile farmGrid² tiles with border, 0–1 UV boundsGPU machines naturally outscore for tiles
Bake offloadSingle task (whole bake)Only the top-scoring sharer may claim
# allocation score — deterministic, in server/src/kiln_server/compute.py
score = 10*cpu + 20*gpu + 5*mem/8 - 30*load - rtt/50
veto if: not sharing · unseen >30s · Blender major.minor mismatch

Current alpha reports deterministic checksums instead of pixels — enough to prove scheduling, allocation, requeue and progress end-to-end. EXR/PNG blob assembly and a Docker sandbox for untrusted farms follow in v0.3 / v1.0. Until then: farm only with people you trust; a .blend can run arbitrary code.

03 — Run it

Two terminals, two Blenders.

# terminal 1 — server
pip install -e ./server
kiln-server --port 8000
# health check → {"ok": true}
curl http://127.0.0.1:8000/healthz
  • Blender 4.2+: zip addon/kiln → Preferences → Install from Disk → enable Kiln Collaborative Editing.
  • Both machines: sidebar (N) → Kiln → same Server URL, same Room (demo), different Names → Connect.
  • Verify: move the default cube. Counters read seq … ↑n ↓m. Then Shared Compute → Share my CPU/GPU → Render Frames 1–4.
  • Stuck? Panel → Test gives latency plus a fix. Export Log writes kiln-debug.txt for issues. Headless check: python examples/debug_probe.py.
